# 最小 Agent 内核架构规划文档

## Pi-like Runtime + Skills + Tools + 多 Agent 共存路线

## 1. 当前结论

你现在的系统应该走这条路线：

```text
最小 Agent Runtime
  + 内置 FollowupResolver
  + 内置 SessionState / TaskState
  + 内置 SkillDiscovery
  + 稳定 ToolRegistry / ToolExecutor
  + AgentLoop 工具调用闭环
  + ResponseSanitizer
  + 外置 Skills 扩展具体能力
  + 后续支持多个 Agent 共存
```

当前不建议优先做：

```text
复杂 Router
复杂 DAG 主流程
默认 PlanExecute
复杂 FinalVerifier
spawn/subagent
多 Agent Supervisor
```

核心判断：

```text
内核只负责“运行机制”；
具体智能能力沉淀为 Skills；
多个长期 Agent 由 Gateway 路由共存；
spawn/subagent 等单 Agent 稳定后再做。
```

# 2. Pi Agent / OpenClaw 的借鉴点

Pi 的定位是一个 **minimal terminal coding harness**，它强调用 Extensions、Skills、Prompt Templates、Themes 来扩展工作流，而不是把所有能力塞进核心。Pi 官方 README 里也明确提到，它跳过了 sub agents 和 plan mode，主张让用户通过扩展包按需构建自己的工作流。([GitHub][1])

OpenClaw 的 Pi 集成思路也很值得借鉴。OpenClaw 文档说明，它不是把 Pi 当作外部子进程或 RPC 服务，而是通过 `createAgentSession()` 嵌入 Pi 的 `AgentSession`，从而控制 session 生命周期、事件处理、工具注入、系统 prompt、session 持久化等。([OpenClaw][2])

OpenClaw 的多 Agent 也不是 Pi 内核自带的 subagent，而是 Gateway 层托管多个隔离 Agent：每个 agent 有自己的 workspace、`SOUL.md`、`AGENTS.md`、可选 `USER.md`、独立 `agentDir` 和 session store。([OpenClaw][3])

所以可以借鉴的核心是：

```text
Pi-like 小核心：
  AgentLoop + Tools + Session + Skills

OpenClaw-like 多 Agent：
  Gateway 路由多个隔离 Agent Profile
```

而不是：

```text
一开始就做复杂多 Agent 编排、DAG、PlanExecute、子 Agent 调度。
```

---

# 3. 你的系统最终定位

建议把系统定位为：

```text
Mateway = Minimal Agent Runtime + Skill System + Tool System + Multi-Agent Profiles
```

其中：

```text
Runtime 负责：
- 配置
- 通道
- 网关
- RuntimeContext
- SessionState
- FollowupResolver
- SkillDiscovery
- ToolRegistry
- AgentLoop
- ResponseSanitizer
- Trace/Event

Skills 负责：
- fresh-search
- source-evaluation
- chinese-summary
- project-review
- code-edit
- doc-writing
- log-analysis
- future planning-mode

Gateway 负责：
- 多 Agent 路由
- channel/account/peer 到 agentId 的绑定
```

这里的关键边界应该再明确一次：

```text
Runtime 内置的是 SkillDiscovery / SkillRegistry 机制；
Skill 内容本身默认放在 workspace / agents 目录中，由运行时动态发现；
不要把用户需要自定义的能力长期硬编码在 Go 源码里。
```

# 4. 最小内核必须包含什么

## 4.1 Config

配置系统只负责系统运行配置，不承载业务逻辑。

至少支持：

```text
model provider
model name
home root
workspace root
agent directory
tool enable/disable
skill enable/disable
max turns
locale
timezone
search config
session config
multi-agent config
```

同时约定：

```text
Mateway 初始化时应在 HOME 下建立 ~/.mateway 目录结构；
workspace 是 runtime 使用的默认工作区；
skills 不应只存在于编译后的内置表中。
```

---

## 4.2 Channel

Channel 只做外部消息适配，例如：

```text
CLI
HTTP API
飞书
微信
网页
终端
```

统一转换为：

```go
type IncomingMessage struct {
    UserID    string
    SessionID string
    Channel   string
    Text      string
    Files     []FileRef
    Metadata  map[string]any
}
```

Channel 不做任务理解，不选工具，不总结。

---

## 4.3 Gateway

Gateway 是外部消息进入 Runtime 的统一入口。

职责：

```text
1. 接收 IncomingMessage
2. 解析 channel/account/peer/thread 信息
3. 根据绑定找到 agentId
4. 加载 AgentProfile
5. 构建 RuntimeContext
6. 调用 AgentKernel
7. 把最终结果交回 Channel
```

Gateway 不做复杂 LLM Router。

---

## 4.4 RuntimeContext

每轮执行都必须注入：

```go
type RuntimeContext struct {
    UserID        string
    SessionID    string
    TaskID       string
    Channel      string

    AgentID       string
    WorkspaceRoot string
    AgentDir      string

    CurrentDate   string
    CurrentTime   string
    Timezone      string
    Locale        string

    UserMessage   string
    ResolvedQuery string
    Files         []FileRef
}
```

重点：

```text
current_date
current_time
timezone
locale=zh-CN
agentId
workspaceRoot
agentDir
```

没有这些，fresh search、followup、SkillDiscovery、多 Agent 隔离都会不稳定。

# 5. Home / Workspace / Agent Directory

推荐目录结构如下：

```text
~/.mateway/
  config/
  logs/
  run/
  trace/
  workspace/
    skills/
    agents/
      main/
        soul.md
        agent.md
        memory.md
        heartbeat.md
        tools.md
        skills/
```

语义分层：

```text
~/.mateway
  运行时 HOME，保存配置、日志、trace、锁文件和默认 workspace。

workspace/skills
  公用 skills，默认给所有 agent 共享。

workspace/agents/main/skills
  main agent 私有 skills，只给 main agent 使用。
```

初始化要求：

```text
1. Mateway 初始化时创建 ~/.mateway 基础目录结构。
2. 至少确保 config / logs / run / trace / workspace 可用。
3. workspace 下应预留 skills/ 和 agents/main/。
4. 默认 skills 应最终落在 workspace/skills，而不是只存在于编译后的内置表中。
5. 如果用户拿到的是成品二进制，程序也必须能在初始化时把默认 skills 模板写入 workspace/skills。
```

成品二进制分发要求：

```text
不要假设用户机器上有源码仓库。
默认 skills 需要作为二进制内置资源或安装包资源随程序分发。
首次初始化时，把这些默认 skills materialize 到 ~/.mateway/workspace/skills。
后续再次启动时，不应粗暴覆盖用户已经修改过的 skill。
```

# 6. Agent Context Files

每个 Agent 都应该有自己的上下文目录。

```text
workspace/agents/main/
  soul.md
  agent.md
  user.md
  memory.md
  heartbeat.md
  tools.md
  skills/
```

建议职责：

```text
soul.md
  Agent 的角色、原则、边界。

agent.md
  Agent 的工作方式、输出规则、执行原则。

user.md
  用户主人的偏好、沟通风格、常见目标、雷区。

memory.md
  长期记忆、项目背景、稳定上下文。

heartbeat.md
  主动检查和惊喜式建议。不要默认注入普通任务 prompt。

tools.md
  工具使用政策、调用协议、禁止事项。
```

`heartbeat.md` 当前可以保持：

```markdown
# heartbeat.md

当前阶段不启用周期任务。
除非用户明确要求定时检查，否则不要主动执行后台任务。
```

普通任务 prompt 的默认注入边界：

```text
每次 planning / planning_repair / synthesis 前，统一注入：

1. 当前日期
2. 用户时区
3. 当前用户请求
4. 当前环境摘要：
   - 操作系统
   - CPU 架构
   - shell
   - HOME
   - workspace
   - project root
   - 常用命令行工具可用性摘要
5. Agent 核心文档：
   - soul.md
   - agent.md
   - user.md
   - memory.md
   - tools.md
6. 当前选中的 skills
7. 当前可用工具

heartbeat.md 不进入普通任务 prompt，只为后续主动任务 / heartbeat 流程保留。
```

# 7. Followup 内置，不做 Skill

你的判断是对的：**followup 应该内置在 Runtime 中**。

原因：

```text
1. 每轮对话前都可能需要 followup 判断。
2. 它依赖 SessionState / TaskState。
3. 它发生在 SkillDiscovery 之前。
4. 它属于对话连续性的基础能力。
```

推荐链路：

```text
IncomingMessage
  -> Load SessionState
  -> TaskBindingResolver
  -> ResolvedQuery / TaskBindingDecision
  -> SkillDiscovery
  -> AgentLoop
```

## 7.1 FollowupResolver 结构

```go
type FollowupDecision struct {
    Kind          string  `json:"kind"`
    TargetTaskID  string  `json:"target_task_id"`
    SourceTaskID  string  `json:"source_task_id"`
    ResolvedQuery string  `json:"resolved_query"`
    Reason        string  `json:"reason"`
    Confidence    float64 `json:"confidence"`
}
```

原则：

```text
1. 不单独先判 is_followup。
2. 先做 task binding，followup 只是绑定结果的一种。
3. 批准、选项、补参数这类强结构输入优先走代码解析。
4. 当前任务续做、切回 open task、历史 continuation 这类弱结构输入交给模型解析。
5. 模型低置信时直接澄清，不猜最近任务。
```

Prompt：

```text
你是 FollowupResolver。

你的任务是判断当前用户输入应该绑定到哪个任务，并把它改写成一个完整、可独立执行的问题。

不要回答用户问题，只输出 JSON。

当前用户输入：
{{current_message}}

最近对话：
{{recent_turns}}

当前活动任务：
{{active_task}}

其他 open tasks：
{{open_tasks}}

历史候选 tasks：
{{history_tasks}}

判断规则：
1. 先判断是否应绑定当前活动任务。
2. 再判断是否应绑定其他 open task。
3. 再判断是否应作为历史 continuation。
4. 不清楚时输出 ambiguous，不要猜测。
5. resolved_query 要保留用户真实意图，不要扩展过度。

输出：
{
  "kind": "active_followup|open_task_followup|historical_continuation|new_task|ambiguous",
  "target_task_id": "",
  "source_task_id": "",
  "resolved_query": "",
  "reason": "",
  "confidence": 0.0
}
```

# 8. SkillDiscovery 必须内置

SkillDiscovery 是内核能力，不是普通 Skill。

必须包含：

```text
SkillLoader
SkillRegistry
SkillSelector
SkillInjector
```

Skill 内容采用 workspace + agent 双层发现：

```text
workspace/skills/
  skill-name/
    SKILL.md
    agents/
      openai.yaml
    references/
    scripts/
    assets/

workspace/agents/main/skills/
  skill-name/
    SKILL.md
    agents/
      openai.yaml
    references/
    scripts/
    assets/
```

`SKILL.md` 最小格式：

```markdown
---
name: project-review
description: Use this skill when the user asks to review, inspect, understand, analyze, or summarize a software project or codebase.
---

# Project Review

...
```

`agents/openai.yaml` 建议存在，用于承载 UI / 市场兼容元数据。

发现顺序建议：

```text
1. workspace/agents/<agent_id>/skills
2. workspace/skills
3. 仅在初始化或修复缺失模板时，才从二进制内置默认模板恢复到 workspace/skills
```

覆盖规则建议：

```text
同名 skill 优先使用 agent 私有版本；
其次使用 workspace 公用版本；
二进制内置模板只用于初始化或补缺，不作为日常运行时直接执行来源。
```

运行机制：

```text
启动时：
  扫描 workspace/skills 和 workspace/agents/<agent_id>/skills
  读取 SKILL.md frontmatter
  只加载 name + description + tags + priority

运行时：
  根据 resolved_query 选择 skills
  读取被选中 skill 的完整 SKILL.md
  注入 Agent Prompt
```

不要把所有 Skill 全文都塞给模型。

# 9. Tool System：少而稳

最小工具建议：

```text
file.list
file.read
file.search
file.apply_patch

project.index
file.summary

web.search
time.now
```

暂不建议一开始暴露太多工具。

## 9.1 文件修改优先 apply_patch

优先：

```text
file.apply_patch
```

而不是：

```text
write_file 全量覆盖
```

原因：

```text
1. 可审计
2. 可回滚
3. 更适合代码修改
4. 不容易全量覆盖出错
5. 更接近主流 coding agent 的工作方式
```

# 10. AgentLoop 是内核核心

正确流程：

```text
model output
  -> tool_call
  -> runtime parse
  -> execute tool
  -> append tool_result
  -> model continue
  -> final_answer
  -> user
```

用户不能看到：

```text
<tool_call>
<invoke>
...
</invoke>
```

## 10.1 最小 JSON 协议

工具调用：

```json
{
  "type": "tool_call",
  "calls": [
    {
      "id": "call_1",
      "name": "file.read",
      "args": {
        "path": "internal/gateway/gateway.go"
      }
    }
  ]
}
```

最终回答：

```json
{
  "type": "final_answer",
  "content": "这里是给用户看的中文回答。"
}
```

Runtime 只把 `final_answer.content` 发给用户。

# 12. SessionState / TaskState 必须内置

Pi-like 系统的重点之一就是 session 持久化。OpenClaw 的多 Agent 文档也强调每个 agent 有独立 session store。([OpenClaw][3])

最小 TaskState：

```go
type TaskState struct {
    ID                   string
    ParentTaskID         string
    ContinuationOfTaskID string
    Status               string
    Topic                string
    UserText             string
    ResolvedQuery        string
    LastAnswer           string
    SelectedSkills       []string
    ToolNames            []string
    PendingFields        map[string]string
    PendingQuestions     []string
    PendingApproval      *PendingApproval
    Artifacts            []Artifact
    StartedAt            time.Time
    FinishedAt           time.Time
    UpdatedAt            time.Time
}
```

每轮结束保存：

```text
topic
resolved_query
selected_skills
tool calls summary
pending_fields / pending_approval
artifacts
final answer
```

下一轮 FollowupResolver 用它判断追问。

# 13. 多 Agent 共存规划

这是本次新增的重要规划。

要区分：

```text
1. 多个 Agent 共存
   多个长期存在的独立 Agent Profile。

2. spawn/subagent
   某个父 Agent 在一次任务中临时派生子 Agent。
```

你现在应该先做 **多个 Agent 共存**，不要先做 spawn。

---

## 13.1 OpenClaw 的多 Agent 模型

OpenClaw 的多 Agent 文档说明，每个 agent 都有自己的 workspace、bootstrap 文件、`agentDir` 和 session store；Gateway 可以根据 channel/account/peer 等路由到不同 agent。([OpenClaw][3])

它的多 Agent 本质是：

```text
Gateway 侧路由多个隔离 Agent
```

而不是：

```text
Pi 内核自带 subagent 调度
```

---

## 13.2 你应该如何实现多 Agent 共存

目录：

```text
agents/
  main/
    soul.md
    agent.md
    memory.md
    skills/

  coding/
    soul.md
    agent.md
    memory.md
    skills/

  research/
    soul.md
    agent.md
    memory.md
    skills/

  ops/
    soul.md
    agent.md
    memory.md
    skills/
```

每个 Agent 拥有：

```text
agentId
workspaceRoot
agentDir
sessionStore
contextFiles
skill allowlist
tool allowlist
model selection
heartbeat config
channel bindings
```

结构：

```go
type ModelSelection struct {
    Default   string
    Fallbacks []string
    Roles     map[string]string
}

type HeartbeatConfig struct {
    Enabled    bool
    Interval   string
    QuietHours struct {
        Start string
        End   string
    }
}

type AgentProfile struct {
    ID             string
    Name           string

    WorkspaceRoot  string
    AgentDir       string
    SessionDir     string

    SessionNamespace string
    Model            ModelSelection
    Heartbeat        HeartbeatConfig

    SkillAllowlist   []string
    SkillDenylist    []string
    ToolAllowlist    []string
    ToolDenylist     []string

    IsDefault      bool
}
```

模型配置原则：

```text
1. ~/.mateway/config/models/*.yaml 只声明模型端点与凭据来源
2. 顶层 model.default 定义单 agent 兼容默认模型
3. agents.profiles[].model.default 定义 agent 自己的默认模型
4. agents.profiles[].model.fallbacks 只定义降级顺序，不隐式抢占默认
5. agents.profiles[].model.roles 为 planning / repair / synthesis / followup 等阶段预留
```

示例：

```yaml
model:
  default: minimax
  fallbacks:
    - local-mlx

agents:
  default: main
  profiles:
    - id: main
      name: 主助理
      model:
        default: minimax
        fallbacks: [local-mlx]
        roles:
          planning: minimax
          repair: minimax
          synthesis: minimax
          followup: local-mlx
      heartbeat:
        enabled: false
        interval: 30m
        quiet_hours:
          start: "23:00"
          end: "08:00"
      skills:
        allow: []
        deny: []
      tools:
        allow: []
        deny: []
      session_namespace: main
```

绑定：

```go
type AgentBinding struct {
    Channel   string
    AccountID string
    PeerID    string
    AgentID   string
}
```

路由优先级：

```text
1. peerId 精确绑定
2. accountId 绑定
3. channel 默认绑定
4. fallback default agent
```

## 13.3 多 Agent 共存什么时候做

建议放在 **P1**。

前提是 P0 单 Agent 已经稳定：

```text
AgentLoop 工具调用闭环
SessionState
SkillDiscovery
ToolRegistry
ResponseSanitizer
```

多 Agent 共存不需要复杂推理，只是 Gateway 加一层 `agentId` 路由，因此可以较早做。

它能解决：

```text
1. 不同用户隔离
2. 不同项目隔离
3. coding / research / ops 分角色
4. 不同 channel 绑定不同 Agent
5. 权限和账号认证更清晰
```

---

# 14. spawn/subagent 规划

spawn/subagent 先不要做。

spawn 的含义是：

```text
父 Agent 在当前任务中临时创建一个子 session / 子 Agent 来完成子任务。
```

适合：

```text
大型项目 review：
  architecture reviewer
  tool system reviewer
  security reviewer

多来源调研：
  official docs researcher
  GitHub/issues researcher
  market/news researcher

代码修改：
  implementer
  reviewer
  tester
```

但它会带来复杂度：

```text
1. 父 Agent 何时 spawn 很难控制
2. 子 Agent 工具权限难管
3. 子 Agent 上下文边界难管
4. 子任务结果如何验收复杂
5. 并发和成本上升
6. debug 困难
```

因此建议放到 **P3/P4**。

---

## 14.1 spawn 需要的前置条件

只有满足这些，再考虑：

```text
1. 单 Agent Loop 非常稳定
2. SessionState 可可靠保存和恢复
3. SkillDiscovery 已经稳定
4. Tool 权限可按 agent/subagent 限制
5. 有父子 session 关系
6. 有结果汇总协议
7. 有并发和成本限制
8. 有实际任务需要并行或委派
```

未来接口可以是：

```go
type SpawnRequest struct {
    ParentSessionID string
    Role            string
    Task            string
    ToolAllowlist   []string
    SkillAllowlist  []string
    ContextBudget   int
}
```

# 15. Agent 间通信规划

在 spawn 之前，可以先做 **多个已存在 Agent 之间的通信**。

这不同于 subagent。

```text
多 Agent 共存：
  coding agent
  research agent
  ops agent

Agent 间通信：
  main agent 给 research agent 发一个任务
  research agent 返回结果
```

可以放到 **P2**。

接口：

```text
agent.send_message(agentId, message)
agent.read_reply(agentId, taskId)
```

但注意：这不是当前 P0/P1 的核心，可以后置。

# 16. DAG 的定位

当前不建议把 DAG 作为主执行流。

不要做：

```text
DAG Router
DAG Planner
DAG Executor
DAG Verifier
```

DAG 以后可以用于确定性内部流程，比如：

```text
search -> filter -> summarize
project.index -> file.summary -> review
read -> patch -> confirm -> apply
skill install -> validate -> index
```

定位：

```text
主流程：AgentLoop
局部稳定流程：未来可以 DAG 化
```

---

# 17. PlanExecute 的定位

当前不建议默认使用 PlanExecute。

Pi 的公开说明里提到它跳过了 sub agents 和 plan mode，把这类能力留给用户通过扩展实现。([GitHub][1])

你也已经实测过：

```text
复杂路由 + PlanExecute + FinalVerifier
会导致耗时、失败率高、验收卡死。
```

所以当前建议：

```text
默认：AgentLoop
未来：planning-mode skill
```

只有当用户明确要求：

```text
制定计划
分步骤执行
复杂多阶段改造
```

才启用 planning skill。

# 18. 多 Agent、spawn、DAG、PlanExecute 对比

| 机制             | 作用                         | 当前阶段建议       |
| -------------- | -------------------------- | ------------ |
| 单 AgentLoop    | 默认执行循环                     | P0 必须做       |
| SkillDiscovery | 能力扩展                       | P0 必须做       |
| 多 Agent 共存     | 多个长期隔离 Agent               | P1 做         |
| Agent 间通信      | 已存在 Agent 互相发任务            | P2 做         |
| spawn/subagent | 父 Agent 临时创建子 Agent        | P3/P4        |
| DAG            | 确定性流程编排                    | 后期局部使用       |
| PlanExecute    | Planner/Executor/Replanner | 后期作为可选 Skill |
| Supervisor     | 复杂多 Agent 调度               | 暂不做          |

# 23. 最终决策

```text

  AgentLoop
```
