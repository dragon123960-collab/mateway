# 飞书测试与验收

这份文档的目标只有一个：

- 让你通过几轮和飞书机器人的对话，一次看懂项目现在会产出什么、写到哪里、成功和失败分别长什么样。

## 1. 测试前准备

本地建议先确认：

```bash
go test ./...
GOCACHE=/tmp/mateway-gocache go build -o build/mateway ./cmd/mateway
./scripts/restart-launchd-service.sh
curl -sS http://127.0.0.1:8787/health
```

如果最后返回 `ok`，说明 gateway 正常。

如果你想彻底从零开始验证新记忆体系，再手动执行：

```bash
mateway memory rebuild --force --drop-all
```

这会清空当前 workspace 的全部 `memory/`。

## 2. 测试 1：直接问答

### 发给飞书的话

```text
你好
```

### 期望现象

- 机器人正常回复
- 这是一个 `answer` 类型的顶层任务

### 数据落点

- 原始对话：`memory/sessions/`
- 会话摘要：`memory/summaries/`
- 运行轨迹：`memory/runs/`
- 任务主档：`memory/tasks/`
- 任务结果索引：`memory/task_outcomes/`

### 成功长相

- `memory/tasks/<task_id>.json` 存在
- 里面有：
  - `task_type = answer`
  - `completion.summary`
  - `completion.evidence`

## 3. 测试 2：调研任务

### 发给飞书的话

```text
请调研北京 AI 活动并整理结论
```

### 期望现象

- 机器人会走调研类任务
- 当前默认模型如果不适合 `plan_execute`，可能保护性退回 `chatmodel`
- 最终仍然要生成任务主档和完成契约

### 数据落点

- 任务主档：`memory/tasks/`
- 运行轨迹：`memory/runs/`
- 学习报告：`memory/learning/reports/`
- 如有长期可复用经验，可能进入 `memory/wiki/`

### 成功长相

- `memory/tasks/<task_id>.json` 中至少能看到：
  - `task_type = research`
  - `goal`
  - `route`
  - `completion.summary`
  - `completion.evidence`
- `memory/learning/reports/<run_id>.md` 存在

## 4. 测试 3：本机 CLI 学习

### 发给飞书的话

```text
你看看 zsh 下 lark-cli 怎么用
```

### 期望现象

- 任务会被判成 `local_cli`
- 系统优先尝试真实本地环境线索
- 如果命令写错，应该优先给出近似命令提示，而不是直接说没装

### 数据落点

- 任务主档：`memory/tasks/`
- 运行轨迹：`memory/runs/`
- 如果失败：`memory/lessons/` 和可能的 `memory/wiki/notes/failure-*.md`

### 成功长相

- `memory/tasks/<task_id>.json` 有：
  - `task_type = local_cli`
  - `completion.summary`
  - `completion.evidence`

### 失败长相

- `memory/tasks/<task_id>.json` 有 `latest_failure`
- `memory/lessons/` 会新增一条 lesson
- lesson 里通常会有：
  - `failure_kind`
  - `tool_name`
  - `provider_name`
  - `preferred_fallback`
  - `do_not_repeat`

## 5. 测试 4：查看定时任务

### 发给飞书的话

```text
/schedule list
```

### 期望现象

- 直接走命令分发，不需要模型猜
- 返回所有当前定时任务
- 如果某个 schedule 已执行过，输出里可能带最近 `task_id` 或 artifact 线索

### 数据落点

- 任务定义：`memory/schedules/jobs.json`
- schedule 运行历史：`memory/schedules/runs/*.jsonl`
- 最近任务结果：`memory/tasks/<last_task_id>.json`

### 成功长相

- `jobs.json` 里能看到任务定义
- 某些任务的 `state.last_task_id` 已有值

## 6. 测试 5：创建一个新的定时任务

### 第一句发给飞书的话

```text
请帮我创建一个每天早上 9:30 提醒我整理今日任务的定时任务
```

### 第二句

如果机器人要求批准，发：

```text
同意
```

### 期望现象

- 第一轮进入 `waiting_approval`
- 批准后真正执行
- 最终 schedule 写入 `jobs.json`
- 对应会有一个任务主档

### 数据落点

- 任务定义：`memory/schedules/jobs.json`
- 任务主档：`memory/tasks/`
- run 轨迹：`memory/runs/`
- 会话摘要：`memory/summaries/`

### 成功长相

- `jobs.json` 有新 job
- 对应 `task record` 有：
  - `task_type = schedule_task`
  - `completion.primary_artifact` 指向 schedule 名称或相关对象
  - `completion.evidence` 不为空

## 7. 测试 6：追问“成果在哪”

### 发给飞书的话

```text
这个任务成果在哪
```

建议在以下场景后测：

- 新建 schedule 后
- 某个定时任务触发完成后
- 某个调研/代码任务完成后

### 期望现象

- 系统优先读 `TaskRecord.primary_artifact`
- 不应该只靠自由文本猜

### 你应该去看的目录

1. `memory/tasks/<task_id>.json`
2. `memory/artifacts/<task_id>.json`
3. schedule 场景下，再看 `memory/schedules/jobs.json`

### 成功长相

- `primary_artifact` 有明确路径、名称或引用对象

## 8. 测试 7：故意制造失败，观察归档

### 发给飞书的话

```text
请用本机不存在的 abcxyz-cli 看看怎么用
```

### 期望现象

- 很可能失败
- 失败后不只是在聊天里报错
- 系统会把失败经验沉淀下来

### 数据落点

- 任务主档：`memory/tasks/`
- 运行轨迹：`memory/runs/`
- 结构化日志：`memory/logs/`
- lesson：`memory/lessons/`
- 有时还有精选 failure wiki：
  - `memory/wiki/notes/failure-*.md`

### 失败后你该怎么看

1. `memory/tasks/<task_id>.json`
   - 看 `latest_failure`
   - 看 `completion.status`

2. `memory/lessons/*.json`
   - 看 `failure_kind`
   - 看 `preferred_fallback`
   - 看 `do_not_repeat`

3. `memory/runs/<run_id>.json`
   - 看完整 steps 和 events

4. `memory/logs/*.jsonl`
   - 看结构化运行事件

## 9. 成功和失败的统一判断

### 成功

至少应看到：

- `TaskRecord` 存在
- `completion.summary` 不为空
- `completion.evidence` 不为空

对于这些任务，还应该有 `primary_artifact`：

- `schedule_task`
- `code_write`
- `diagnose_task`

### 部分完成

如果有回复，但证据不够、产出物不明确，状态通常应是 `partial`。

### 失败

失败后至少应该能在这些地方找到痕迹：

- `memory/tasks/`
- `memory/runs/`
- `memory/logs/`
- `memory/lessons/`

## 10. 一次看懂：每类数据都在哪

### 你要找“聊天原文”

- `memory/sessions/`

### 你要找“最近任务摘要”

- `memory/summaries/`

### 你要找“完整运行轨迹”

- `memory/runs/`

### 你要找“这次任务最终结果”

- `memory/tasks/`

### 你要找“产出物索引”

- `memory/artifacts/`

### 你要找“失败经验和以后别再犯的规则”

- `memory/lessons/`

### 你要找“定时任务定义和执行历史”

- `memory/schedules/`

### 你要找“精选长期知识”

- `memory/wiki/`

### 你要找“正式复盘报告”

- `memory/learning/reports/`

### 你要找“学习提案”

- `memory/learning/proposals/`

## 11. 你只想快速验收时，最小测试集

按这个顺序发给飞书，基本就能看明白项目运行机制：

1. `你好`
2. `请调研北京 AI 活动并整理结论`
3. `你看看 zsh 下 lark-cli 怎么用`
4. `/schedule list`
5. `请帮我创建一个每天早上 9:30 提醒我整理今日任务的定时任务`
6. `同意`
7. `这个任务成果在哪`
8. `请用本机不存在的 abcxyz-cli 看看怎么用`

如果这 8 轮下来你能同时看懂：

- 任务怎么分类
- 结果写到哪里
- schedule 怎么追
- failure 怎么归档
- lesson 有没有形成

那就说明你已经把项目的主运行机制整明白了。
