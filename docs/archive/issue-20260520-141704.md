# Mateway 测试问题清单

更新时间：2026-05-20

这份文档只记录本轮真实模型批测中暴露出来的问题、证据和影响，不展开修复实现。

## 1. followup 续接对“继续上一轮”不稳定

状态：已处理（2026-05-20）

处理记录：

- 已在 runtime task binding 中接入 `internal/followup.Resolver`，并放在模型 followup 前作为强规则兜底。
- “继续上一轮 / 继续刚才 / 接着刚才 / 展开 / 按刚才”等明确依赖当前活动任务的输入会优先绑定 active task，不再因为模型低置信直接进入 ambiguous。
- “昨天 / 上次 / 之前 / 历史”等可能指向非当前任务的输入仍交给模型结合历史候选判断，避免把历史续接误绑到 active task。
- 已新增回归测试 `TestRuntimeRuleFollowupBeatsLowConfidenceModelAmbiguity`。

### 现象

在连续会话批测里，用户已经明确说了“继续上一轮”，系统仍然经常返回“我还不能确定你是在继续哪个任务”，把任务打成待补充信息。

### 证据

- [`/Users/dongping/.mateway/testdata/2026-05-20/125800-1.md`](/Users/dongping/.mateway/testdata/2026-05-20/125800-1.md)
- [`/Users/dongping/.mateway/testdata/2026-05-20/125836-2.md`](/Users/dongping/.mateway/testdata/2026-05-20/125836-2.md)
- [`/Users/dongping/project/mateway/internal/runtime/task_binding.go`](/Users/dongping/project/mateway/internal/runtime/task_binding.go#L258)
- [`/Users/dongping/project/mateway/internal/model/planner.go`](/Users/dongping/project/mateway/internal/model/planner.go#L206)

### 影响

- 连续会话体验断裂
- 用户明明是在接着上一轮说，系统却反复要求补一句上下文
- `followup` 的核心价值被削弱，尤其是在批量测试和真实对话里很明显

### 可能原因

- `resolveModelFollowup()` 完全依赖模型置信度阈值，低于阈值就直接转成 `ambiguous`
- 提示词里虽然给了 open/history 候选，但对“上一轮任务”没有足够强的确定性兜底
- `continue` 这类明确意图在模型侧仍然可能被判成不明确

## 2. 现有 `internal/followup` 规则没有真正进入主链

状态：已处理（2026-05-20）

处理记录：

- `AgentLoop.resolveTaskBinding()` 当前顺序为：approval reply -> slot fill -> rule followup -> model followup -> new task。
- `internal/followup/resolver.go` 不再只是孤立测试能力，已成为主链 task binding 的本地规则入口。
- 模型 followup 仍保留用于历史任务选择、open task 选择和复杂澄清。

### 现象

仓库里存在一个较完整的 `internal/followup/resolver.go`，里面已经能识别“继续”“重试”“展开”“按刚才这个文件”等 followup 意图，但运行时主链实际走的是 `resolveModelFollowup()`，没有直接消费这个规则化 resolver。

## 4. 批测任务的“通过”不等于答案质量真的足够

状态：已部分处理（2026-05-20）

处理记录：

- `mateway test` 报告新增“质量提示”段。
- 当任务机制完成但回复过短、缺少工具证据、分析型问题证据过少或回复偏工具痕迹时，结论会标为“任务机制已完成，但答案质量需要人工复核”。
- 这不是完整自动评分系统，只是先避免把“跑完”误读为“质量通过”。后续若需要可继续做独立质量评估器。

### 现象

部分测试任务虽然成功落了 Markdown 报告，但内容更像是“工具调用痕迹 + 形式化总结”，不一定真的完成了用户想要的分析深度。例如有些任务只做了文档重述、shell echo 或浅层总结，还是会被记录成已完成。

### 证据

- [`/Users/dongping/project/mateway/testdata/2026-05-20/125922-task.md`](/Users/dongping/project/mateway/testdata/2026-05-20/125922-task.md)
- [`/Users/dongping/project/mateway/testdata/2026-05-20/125940-task.md`](/Users/dongping/project/mateway/testdata/2026-05-20/125940-task.md)
- [`/Users/dongping/project/mateway/testdata/2026-05-20/125913-task.md`](/Users/dongping/project/mateway/testdata/2026-05-20/125913-task.md)

### 影响

- `mateway test` 能验证“机制通不通”，但还不能自动判断“答案够不够好”
- 批量回归容易出现“看上去跑完了，其实质量偏浅”的情况
- 如果后面要把测试结果交给人看，需要额外的质量检查标准

### 可能原因

- 目前测试命令只负责执行和落盘，没有独立的质量评分或失败判定
- 任务模板还没有强制区分“真正分析”与“只是调用工具后做形式总结”

## 5. 复杂中文指令下的计划 JSON 容易被模型生成坏掉

状态：已处理（2026-05-20）

处理记录：

- `internal/model.parsePlan()` 已增加一次本地 JSON 修复兜底，专门处理模型在 JSON 字符串内部输出未转义双引号的情况，例如 `定位"本轮清单"位置`。
- 修复仅在首次 `json.Unmarshal` 失败后触发，且仍要求修复后的内容能被标准 JSON 解析，不放宽整体 JSON schema。
- 已新增 `internal/model/planner_test.go` 覆盖中文引号导致的坏计划解析。

### 现象

在“本地读写与命令执行”测试里，模型先生成了一个带中文引号的计划 JSON，随后在主链解析阶段直接失败，任务还没进入真实工具执行就结束了。

### 证据

- [`/Users/dongping/project/mateway/testdata/2026-05-20/134737-本地读写执行本轮.md`](/Users/dongping/project/mateway/testdata/2026-05-20/134737-本地读写执行本轮.md)
- [`/Users/dongping/project/mateway/docs/测试文档.md`](/Users/dongping/project/mateway/docs/测试文档.md)

### 影响

- 一类本来应该覆盖 `file.read / file.patch / shell.run` 的回归任务，会在计划阶段就失败
- 这会让测试误以为工具链有问题，实际上是计划输出格式不稳
- 复杂任务越明确，越容易触发这个问题，说明计划层对中文任务描述的鲁棒性还不够

### 可能原因

- 计划 JSON 生成没有足够强的格式约束
- 模型会把中文引号直接塞进 JSON 字符串，导致解析失败
- 当前失败恢复逻辑更偏向“换一轮规划”，而不是对坏 JSON 做自动修复

## 6. 2026 最新信息任务仍然会混入二手来源和旧口径

状态：已部分处理（2026-05-20）

处理记录：

- 已增强 `fresh-search` 默认 skill：要求计划搜索时优先构造命中官方/一手来源的 query，对课程、榜单、趋势类任务至少安排官方或原始发布方查询。
- 已增强 `source-evaluation` 默认 skill：要求最终结论标注来源类型，二手榜单、转载页、SEO 聚合页不能单独支撑“最新/最热/官方”结论。
- `web.search` 输出现在会附带来源质量提示，提醒 synthesis 阶段区分 official/primary、authoritative media、secondary roundup、unclear-date。
- 这仍不是硬性来源过滤器；后续若要完全解决，需要在工具层返回结构化来源分类和排序，或新增专门的 source gate。

### 现象

在“AI开源课程最新”和“AI热门趋势最新”测试里，模型确实优先使用了 2026 相关搜索，但结果中仍明显混入：

- 二手文章
- 含糊的榜单页
- 时间戳不够硬的转载页

课程和趋势都能跑完，但“最新”和“权威”之间的区分还不够稳定。

### 证据

- [`/Users/dongping/project/mateway/testdata/2026-05-20/134817-ai.md`](/Users/dongping/project/mateway/testdata/2026-05-20/134817-ai.md)
- [`/Users/dongping/project/mateway/testdata/2026-05-20/134920-ai.md`](/Users/dongping/project/mateway/testdata/2026-05-20/134920-ai.md)

### 影响

- 用户问“最新”时，系统看起来在搜最新，但最后可能仍然引用二手资料
- 趋势和课程类任务更容易给出“像是对的”而不是“可复核”的结果
- 如果后续要做真实外部研究，这个问题会直接影响可信度

### 可能原因

- `fresh-search` 能触发，但缺少更强的来源筛选约束
- `source-evaluation` 目前更像总结辅助，还没有变成硬门槛
- 结果拼接阶段会优先保留语义丰富内容，而不是最权威内容

## 8. 飞书 followup 能接续，但“继续上一轮”没有稳定转成结构化拆解

- 生成的 `resolved_query` 会明确写入“本轮补充要求优先级最高，必须明确执行，不要只复述上一轮主题”。
- 已新增回归测试，验证 B2 这类 followup 会把结构化补充要求传入 planning。

## 11. 安全命令和项目索引任务误入待确认

状态：已处理（2026-05-20）

处理记录：

- runtime 执行阶段不再信任模型对 safe read step 给出的 `requires_confirm=true`，是否需要确认改由工具策略 `RequireConfirmForTool()` 决定。
- 危险 shell、文件写入和 patch 仍由工具策略强制确认；安全只读 shell 不会再因为模型误标而卡住。
- planner 提示已明确“项目概览优先使用 `project.index`，单文件摘要优先用 `file.summary`”，并说明安全只读命令应 `requires_confirm=false`。
- 已新增回归测试覆盖模型把 `pwd` 误标为 `requires_confirm=true` 时仍直接执行。

### 现象

CLI 批测里，C1 安全命令和 D1 项目索引都进入了待确认。C1 本来是安全只读命令，D1 本来应优先走项目索引能力；两者都不应该默认让用户确认。

### 证据

- CLI 观察：C1 安全命令进入待确认
- CLI 观察：D1 项目索引进入待确认

### 影响

- 安全只读任务被误拦截，会让 CLI 体验变重
- 项目理解任务如果被规划成 shell 路径并要求确认，会削弱 `project.index` 工具价值
- 回归报告容易把“安全策略过宽”误看成正常待确认

### 可能原因

- planner 可能倾向使用 `shell.run` 做项目扫描，而不是优先选择 `project.index`
- `shell.run` 或计划里的 `requires_confirm` 对安全只读命令仍然偏保守
- 工具选择提示还没有明确要求“项目概览优先使用 `project.index`，不要用 shell 代替”
- `RequireConfirmForTool()` 和模型计划的 `requires_confirm` 之间的边界还可以继续收紧

## 结论

这轮批测里，最值得优先处理的是：

1. followup 续接稳定性
2. followup 规则和 runtime 主链的接线
3. 测试报告 trace 对齐

`HOME` 作为默认目录本身没有问题，这次主要问题不在默认根，而在 followup 绑定和测试报告可读性上。
